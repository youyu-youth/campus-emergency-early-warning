# 规格：演练端到端最小闭环（路线第 2 步）

Status: ready-for-agent
来源：2026-11-08 grill 会话（决策已录入 docs/design.md 第 9 节、GLOSSARY.md、docs/adr/0001）
上游基座：提交 f635a45（数据库/状态机/时钟/模拟引擎，27 测试绿）

## Problem Statement

演练操作员目前只能"配置一场演练的数据"，却无法真正**跑起来**：基座里有场景模板、信号脚本和状态机，但没有智能体去解读信号、研判等级、派发任务、生成通知和复盘报告。整条"事件模拟 → 感知上报 → 定级派发 → 协同处置 → 通知发布 → 复盘评估"的核心闭环不存在，后续的 UI 也没有可以轮询的数据源。操作员需要一个不依赖界面、用一条命令就能跑完一整场推演并看到完整时间线与复盘报告的后端。

## Solution

实现进程内推演运行器 + 五类智能体 + LangGraph 编排：操作员用 CLI 指定场景与随机种子发起演练，推演按模拟时钟自动推进，在事件定级、任务方案、通知发布三个关键节点自动暂停等待人工确认（或以全自动模式跳过），全程每步落库，结束时生成复盘报告与规则评分。所有智能体调用可注入假模型剧本，使全链路在无网络、无真实模型的条件下可测试、可复现。

## User Stories

1. 作为演练操作员，我想用一条命令指定场景与随机种子发起演练，以便不依赖界面运行完整推演。
2. 作为演练操作员，我想固定随机种子重跑得到一致的推演结果，以便在课堂上演示和对比。
3. 作为演练操作员，我想在命令行实时看到推演时间线逐条打印，以便观察当前进展。
4. 作为演练操作员，我想在事件定级节点被暂停并看到指挥调度的建议等级与理由，以便人工确认。
5. 作为演练操作员，我想在任务方案节点被暂停并看到任务清单（角色/标题/说明），以便确认或调整。
6. 作为演练操作员，我想就地调整建议（改等级、增删改派任务）后继续执行，以便体现人工指挥权。
7. 作为演练操作员，我想在通知发布节点看到通知全文并确认发布，以便把关对外文案。
8. 作为演练操作员，我想用全自动模式跳过全部确认点，以便快速跑通或做回归。
9. 作为演练操作员，我想暂停和恢复演练，以便控制课堂节奏。
10. 作为演练操作员，我想调整演练倍速，以便加快或放慢推演。
11. 作为演练操作员，我想终止演练并得到明确的终态记录，以便放弃失控的推演。
12. 作为演练操作员，我想在演练结束时看到复盘报告（时间线归纳、指标、问题分析、改进建议）与总评分，以便组织课后讲评。
13. 作为演练操作员，我想查看任一时间线节点的原始输入、决策依据与结构化输出，以便解释"系统为什么这么做"。
14. 作为演练操作员，我想在进程意外重启后找回进行中的演练（恢复为暂停态），以便不丢失推演进度。
15. 作为校园安全监测员，我想看到每个模拟信号被感知智能体解读为位置/类型/时间/证据并上报为事件，以便理解信号到事件的转化。
16. 作为校园安全监测员，我想看到同一场演练的后续信号作为补充证据关联到同一事件，以便保持单事件焦点。
17. 作为课程演示者，我想让所有演练数据、通知与报告都带显著的「模拟演练」标识，以便绝不与真实警情混淆。
18. 作为课程演示者，我想看到模拟时间与真实时间并列标注（日志注明时间来源），以便讲解两套时间的区别。
19. 作为课程演示者，我想看到保安/医务/后勤任务并行执行并各自反馈耗时、资源消耗与结果，以便展示多智能体协同。
20. 作为课程演示者，我想看到场景演变里程碑（如烟雾扩散）出现在时间线上并可能触发重新调度评估，以便展示动态指挥。
21. 作为平台维护者，我想用假模型剧本在 CI 跑通全链路测试，以便不依赖网络与真实模型也能验证核心流程。
22. 作为平台维护者，我想向假模型注入坏输出，以便验证智能体降级路径（异常节点 + 重试 + 不阻塞他人）。
23. 作为平台维护者，我想让每个智能体调用受超时约束，以便单个模型卡死不拖垮整场演练。
24. 作为平台维护者，我想让通知模拟分发失败只影响通知本身，以便主线推演不被打断。
25. 作为平台维护者，我想让数据库成为推演进度的唯一事实来源（每步落库），以便运行器随时可重建。
26. 作为平台维护者，我想限制同一时间至多一场运行中的演练，以便保证单事件焦点的产品语义。
27. 作为平台维护者，我想让评分由规则而非模型计算，以便同一输入得到同一分数。

## Implementation Decisions

1. **五类智能体模块**：监测感知、指挥调度、处置执行（保安/医务/后勤三角色共用接口、按角色分化提示词与规则参数）、通知发布、复盘评估。每个智能体包含：zod 输入协议、zod 输出协议、中文提示词、超时与降级策略。输出必须经运行时校验。
2. **模型适配器注入**：智能体只依赖 LangChain 的 ChatModel 接口；测试注入可编排剧本的假模型（按"智能体 + 调用序"返回预设响应，支持注入坏 JSON 与超时），生产后续注入 DeepSeek（路线第 3 步，不在本规格内）。
3. **LangGraph 编排**：共享状态为强类型图状态；节点对应智能体步骤；处置阶段对三角色任务并行扇出/汇合；三个关键节点（定级、任务方案、通知发布）以中断机制暂停图执行等待确认。
4. **进程内推演运行器**（见 docs/adr/0001）：服务端进程内唯一实例，tick 循环驱动模拟时钟、信号到期、演变里程碑与图步进；对外操作：发起、暂停、恢复、调速、确认、调整后执行、终止。同一时间至多一场 running 演练。
5. **确认语义**：进入关键节点 → 演练状态 `awaiting_confirmation` 且模拟时钟同步停走；确认或调整后恢复 `running`。确认等待不限时（教学场景）。
6. **LLM 与规则分工**（AGENTS.md 第 5 节）：LLM 只负责解读信号、提出定级建议与理由、制定任务方案、生成执行叙述与通知文案、产出复盘分析；信号时序、演变、任务耗时、资源消耗、送达统计、任务成败与总评分全部由规则 + 种子确定性计算。
7. **降级策略**：智能体输出无效或超时 → 重试一次 → 仍失败则采用规则默认结果继续推进，时间线记 `anomaly` 节点（含降级说明）；通知失败不影响主线。
8. **Schema 变更**：新增 `reports` 表（迁移 `0002_reports`，追加式，不破坏历史数据），复盘报告整行关联演练，内容含时间线归纳、指标、问题分析、改进建议。
9. **时间线写入**：闭环全程写 `timeline_nodes`，节点类型对齐现有八类（signal/grading/dispatch/feedback/status_change/notification/anomaly/operator_action）；`detail` 存原始输入、决策依据、结构化输出三段 JSON；⚑ 节点 `requires_confirmation=1` 并记录确认耗时；`sim_time` 与 `real_time` 同时落库。
10. **信号→事件**：首个到期信号经感知智能体解读后创建事件（`reported`）；同场景后续信号作为补充证据节点关联同一事件，不新开事件（单事件焦点）。
11. **重新调度（最小版）**：演变里程碑到达时，指挥调度智能体评估是否需要加派或调整任务；若需要，经同一确认缝放行后派发。
12. **恢复语义**（补充 ADR 0001）：进程重启后，原 `running` 演练恢复为 `paused`，由操作员手动恢复；时钟从落库状态续算。
13. **CLI**：`pnpm drill:run`，参数含场景键、随机种子、强度/地点、确认开关（`--auto` 为全自动）；确认节点在终端交互式展示建议并等待选择；结束时打印复盘摘要与总评分。CLI 是运行器之上的薄打印层，不含业务规则。
14. **通知**：每事件生成师生、家长两个受众的通知；内容带「模拟演练」标识文案；确认后置为 `published_sim`，送达统计由规则按种子计算写入 `delivery`。
15. **评分**：规则计算（总时长、发现→上报耗时、定级耗时、任务完成率、资源消耗加权）写入 `drills.score`；复盘智能体只产出分析与建议，不算分。

## Testing Decisions

- **只测外部行为**：通过两条已与操作员确认的缝断言可观察结果（数据库行、运行器状态、智能体结构化输出），不断言内部实现细节。
- **缝 1 · 推演运行器（主缝）**：固定场景 + 种子 + 假模型剧本，从发起驱动到终态，断言：事件定级与等级、任务派发/并行执行/反馈、通知发布与送达统计、时间线节点顺序与 ⚑ 标记、复盘报告存在且内容来源可溯源、`drills.score` 存在、演练终态 `completed`；另断言暂停/恢复/调速/终止/确认/调整的状态机流转，以及"重启后恢复为 paused"。
- **缝 2 · 智能体边界（次级缝）**：每类智能体注入正常剧本 → 输出解析正确；注入坏 JSON / 超时 → 走降级路径。
- **确定性**：全部测试使用假模型 + 固定种子，无网络、无真实模型、无真实时间依赖（时钟注入真实时刻参数）。
- **AGENTS.md 必测清单映射**：异常信号上报（缝 1+2）、事件分级（缝 1+2）、任务分配（缝 1）、处置反馈（缝 1）、Graph 路由（缝 1 的确认暂停/并行汇合）、输出解析（缝 2）。
- **先例**：沿用现有 vitest 纯函数测试风格（state-machines / clock / engine / db 测试）。

## Out of Scope

- 真实模型（DeepSeek）接入——路线第 3 步，独立规格。
- 一切 UI 页面与 API 路由（含轮询接口）——路线第 4 步；本步只保证运行器可在服务端进程内被后续路由调用。
- SSE / 实时推送基础设施（已定为轮询）。
- 手动注入测试信号（design.md 未决项，倾向二期）。
- 复盘报告导出格式（PRODUCT.md 未决项）。
- 登录、鉴权、多用户（一期单机无登录）。
